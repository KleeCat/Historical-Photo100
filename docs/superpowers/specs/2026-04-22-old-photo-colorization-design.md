# 老照片彩色化 GUI 集成设计

## 1. 背景与目标

### 1.1 背景

当前项目已经具备基于 PySide 的图形界面、超分辨率处理流程、后台处理线程以及输出结果展示能力。答辩老师建议补充“将老照片变彩色”的功能，以增强系统对历史照片修复场景的完整性表达。

### 1.2 目标

在现有 GUI 中新增一个**独立的老照片彩色化功能**，与现有超分辨率功能并列展示，满足以下目标：

- 支持导入单张黑白老照片并生成彩色结果；
- 彩色化能力在界面中有清晰独立入口，便于答辩讲解；
- 模型权重可提前下载，答辩现场离线运行；
- 默认按 **CPU-only** 环境设计；
- 更重视结果效果与演示稳定性，而非极致速度；
- 结果可视化展示并保存到输出目录。

## 2. 约束与假设

### 2.1 已确认约束

- 集成形式：集成到现有 GUI；
- 功能形态：与超分辨率分开，提供两个独立按钮；
- 部署方式：模型提前下载，现场离线运行；
- 优先级：效果优先；
- 推理环境：CPU-only；
- 可接受耗时：单张图片 30～60 秒。

### 2.2 设计假设

- 第一版只聚焦**单图彩色化**；
- 第一版不做复杂手工交互上色；
- 第一版不要求批量彩色化；
- 模型后端采用本地离线预训练彩色化模型，接口设计允许后续替换具体模型实现；
- 若输入图像过大，可在彩色化流程中做适度缩放，以平衡 CPU 时延与视觉效果。

## 3. 范围界定

### 3.1 本次纳入范围

- GUI 新增“开始彩色化”入口；
- 新增独立彩色化模块；
- 使用后台线程执行彩色化推理；
- 本地模型检查、加载、推理、结果保存；
- 处理成功/失败/取消等状态反馈；
- 右侧结果区显示彩色化结果；
- 输出目录保存彩色化结果图。

### 3.2 暂不纳入范围

- 批量彩色化；
- 手动指定区域颜色；
- 多彩色化模型切换 UI；
- 彩色化参数复杂调优面板；
- “彩色化后自动超分辨率”的串联功能；
- 在线 API 或联网推理。

## 4. 方案对比与选型

### 4.1 方案 A：彩色化并入现有“开始修复”流程

优点：

- 改动较少；
- 实现速度快。

缺点：

- 彩色化与超分辨率边界不清晰；
- 不利于答辩时单独说明“新增彩色化能力”；
- 后续维护和扩展混乱。

### 4.2 方案 B：新增独立彩色化模块与按钮（推荐）

优点：

- 与超分辨率能力解耦，结构清晰；
- GUI 入口直观，适合答辩演示；
- 方便后续扩展串联处理流程；
- 更符合现有项目的模块化组织方式。

缺点：

- 需要补充新的线程、流程和模型调用逻辑；
- 初期改动比方案 A 稍大。

### 4.3 方案 C：直接做“一键老照片修复”

优点：

- 展示效果更完整。

缺点：

- CPU-only 环境下耗时和风险更高；
- 彩色化本身会被“综合修复”流程弱化；
- 不利于老师直接看到新增功能点。

### 4.4 结论

采用**方案 B**：在现有 GUI 中新增独立彩色化入口，并将彩色化能力实现为独立模块，与现有超分辨率功能并列。

## 5. 最终设计

### 5.1 用户交互设计

用户操作流程如下：

1. 打开一张黑白老照片；
2. 在侧边栏点击“开始彩色化”；
3. 系统在后台线程中执行彩色化推理；
4. 处理过程中界面显示状态与进度；
5. 处理完成后右侧显示彩色结果图；
6. 结果自动保存到输出目录；
7. 用户可继续单独运行超分辨率功能。

### 5.2 架构分层

建议保持现有分层方式：

- `sidebar.py`：负责彩色化按钮等界面控件；
- `main.py`：负责流程调度、信号连接、状态管理；
- `workers.py`：负责后台线程执行；
- `colorization.py`：负责彩色化模型检查、加载、推理与结果保存；
- `processing.py`：继续负责现有超分辨率与相关处理逻辑。

### 5.3 文件改造清单

#### 新增文件

- `gui_pyside/colorization.py`
  - 封装彩色化主流程；
  - 对外暴露高层入口，如 `run_colorization_pipeline(...)`；
  - 内部负责模型路径检查、预处理、推理、后处理、保存结果。

#### 修改文件

- `gui_pyside/sidebar.py`
  - 新增“开始彩色化”按钮；
  - 使其与现有超分辨率主按钮并列；
  - 在处理状态切换中纳入按钮禁用/恢复逻辑。

- `gui_pyside/main.py`
  - 连接彩色化按钮点击事件；
  - 新增彩色化任务启动逻辑；
  - 新增彩色化完成、失败、取消回调；
  - 在已有处理状态管理中统一纳入彩色化 worker。

- `gui_pyside/workers.py`
  - 新增 `ColorizeWorker`；
  - 在 QThread 中调用 `colorization.py`；
  - 发出进度、结果、完成状态等信号；
  - 支持取消请求。

#### 新增模型目录约定

- `models/colorization/`
  - 用于存放彩色化模型权重；
  - 答辩前手动准备；
  - 运行时若缺失则给出明确提示。

## 6. 模块设计细节

### 6.1 `gui_pyside/colorization.py`

建议职责：

- 检查模型文件是否存在；
- 按需加载本地彩色化模型；
- 将输入图像转换为模型需要的尺寸与颜色空间；
- 在 CPU 上执行推理；
- 对输出结果做后处理并恢复展示/保存格式；
- 将结果保存到输出目录并返回结构化结果。

建议接口风格：

- `get_colorization_model_status(...)`
- `load_colorization_model(...)`
- `run_colorization_pipeline(...)`

其中，GUI 和 worker 只依赖高层入口，避免直接耦合模型细节。

### 6.2 `ColorizeWorker`

建议信号与职责参考现有 `ProcessWorker` 风格：

- 进度信号：提示“检查模型 / 加载模型 / 执行彩色化 / 保存结果”等阶段；
- 图像结果信号：将最终彩色图发回主线程；
- 完成信号：携带成功状态与提示文本；
- 中断支持：允许用户点击取消。

### 6.3 `main.py` 调度逻辑

建议新增彩色化流程控制方法，例如：

- `start_colorization()`
- `_on_colorize_progress(...)`
- `_on_colorize_image_ready(...)`
- `_on_colorize_finished(...)`

设计原则：

- `main.py` 不写模型推理逻辑；
- 只负责输入检查、状态切换、信号连接和结果展示；
- 确保同一时刻只运行一个耗时任务，避免与现有超分线程冲突。

### 6.4 `sidebar.py` 交互逻辑

建议界面上保留两个清晰入口：

- 超分辨率；
- 彩色化。

第一版不加入复杂参数面板，减少答辩前开发风险。按钮文本应尽量中文化、直观化，便于答辩老师直接理解。

## 7. 数据流设计

彩色化处理数据流：

1. 用户选择输入图像；
2. `main.py` 检查任务状态与输入有效性；
3. 创建 `ColorizeWorker`；
4. `ColorizeWorker` 调用 `run_colorization_pipeline(...)`；
5. `colorization.py` 检查 `models/colorization/` 中模型权重；
6. 读取图片并执行预处理；
7. 本地 CPU 推理生成彩色结果；
8. 保存结果图到输出目录；
9. 将结果图与状态信息回传 `main.py`；
10. GUI 更新预览和状态栏。

## 8. 错误处理设计

至少覆盖以下情况：

### 8.1 未打开图片

提示示例：

- “请先打开一张图片再进行彩色化”

### 8.2 模型文件缺失

提示示例：

- “未找到彩色化模型，请检查 `models/colorization` 目录”

### 8.3 图片读取失败

提示示例：

- “图片读取失败，请确认文件格式是否正确”

### 8.4 推理失败

提示示例：

- “彩色化处理失败：{具体错误}”

### 8.5 用户取消

提示示例：

- “已取消彩色化任务”

## 9. 性能与演示策略

考虑到答辩环境为 CPU-only，建议采用以下策略：

- 第一版仅保证单图稳定运行；
- 若输入分辨率过大，可增加内部缩放策略；
- 优先保证最终视觉效果和成功率；
- 答辩演示时提前准备 1～2 张尺寸适中、效果明显的黑白老照片；
- 输出目录中保留原图与彩色结果，必要时补充对比图，便于讲解。

## 10. 测试与验证

### 10.1 功能验证

- 可成功加载单张黑白图片；
- 点击“开始彩色化”后不会阻塞主界面；
- 彩色结果能正常显示；
- 结果图能保存到指定目录；
- 连续运行多次不崩溃；
- 与超分辨率流程互斥正常。

### 10.2 异常验证

- 无输入图像时给出清晰提示；
- 缺少模型权重时给出清晰提示；
- 非法图片文件可被拦截；
- 彩色化线程可取消；
- 任务失败后界面状态能恢复。

### 10.3 答辩验证

- 在离线环境中启动程序；
- 不依赖网络加载模型；
- CPU 上单张图片可在可接受时间内完成；
- 演示路径清晰：导入 → 彩色化 → 展示结果 → 保存结果。

## 11. 风险与缓解

### 风险 1：CPU 推理过慢

缓解：

- 控制演示图片尺寸；
- 优先准备适合展示的样例图；
- 必要时增加推理前缩放。

### 风险 2：模型依赖复杂

缓解：

- 将模型调用封装到独立 `colorization.py`；
- 提前固定依赖版本与模型路径；
- 优先保证第一版单一后端可跑通。

### 风险 3：界面流程与现有超分逻辑冲突

缓解：

- 在 `main.py` 中统一管理当前活动 worker；
- 明确彩色化与超分辨率任务互斥；
- 沿用现有线程与状态切换模式。

## 12. 结论

本设计选择在现有 GUI 中新增一个**结构清晰、离线可用、适合答辩展示**的老照片彩色化模块。第一版聚焦单图彩色化、结果显示、保存与稳定运行，不扩展非刚需功能。实现上采用独立 `colorization.py` + `ColorizeWorker` + GUI 并列按钮的方式，兼顾答辩展示效果、工程结构清晰度和落地风险控制。
